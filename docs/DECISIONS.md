## A. 底座与技术路线

### D-01 继续在 `tieba_sign_android` 上更新，不换到 `tieba_sign_app`

- **结论**：同一款 App 上继续迭代，不换代码底座。`tieba_sign_app` 留作通用模板，它不是前进路线。
- **理由**：本项目业务代码完整（`app/main.py` 58 KB + signer / autosign / weblogin / tieba_api
  + `p4a_local/aiotieba` 定制配方 + `java_src` 的 KeystoreHelper），约 118 KB。换底座等于全部
  移植一遍，还要冒"老用户 Keystore 密文解不开、必须重新登录"的风险。收益（目录更整齐）
  与代价不成比例。
- **代价**：目录里保留了一些历史包袱（`_legacy/` 等），接受。
- **出处**：`ROADMAP.md`「已定下的路线（不要再动摇）」

### D-02 Python + aiotieba，而不是原生 Java/Kotlin 重写

- **结论**：业务逻辑全部在 Python 侧，Java 只做 Python 拿不到的 Android 能力（Keystore、前台服务、安装入口）。
- **理由**：aiotieba 已经把贴吧协议、签名、加密都封装好了，重写等于重做全部逆向工作。
- **出处**：`README.md`「技术架构」

### D-03 用 python-for-android 的 webview bootstrap，不用 Kivy / SDL

- **结论**：Python 在 `127.0.0.1:5000` 起本地 HTTP 服务，WebView 渲染 MD3 前端。
- **理由**：省掉 Kivy/SDL 一大层依赖和体积；前端用 HTML/CSS 写 MD3 比 Kivy 手搓控件快得多，
  深色模式也只是 CSS token 的事。
- **代价**：多一个本地端口的生命周期要管；WebView 与 Python 之间靠 HTTP 通信。
- **出处**：`README.md`「技术架构」

### D-04 aiotieba 钉死 4.7.1，禁止"顺手升级"

- **结论**：`vendor/aiotieba-4.7.1.tar.gz` 是不可变依赖，和包名、签名同级。
- **理由**：`Client.add_post(fname, tid, content)`（主楼回复）在 4.7.1 里有；上游 4.8.1 已把
  `src/aiotieba/api/add_post/` **整个删掉**（该路径 404，`client.py` 的 import 清单里也没有），
  升上去「自动水贴 / 一键水贴」整体失效。PyPI 上根本没有 4.x（最高 3.3.0），这份是从 GitHub tag 打的包。
- **核实方式**：2026-10-15 用 GitHub API 对过 `v4.7.1` 与 `v4.8.1` 的 `api/add_post` 目录，并查了 PyPI 版本列表。
- **出处**：`ROADMAP.md`「第四条：aiotieba 依赖被钉死在 4.7.1」

## B. 安全与身份

### D-05 BDUSS 用 Android Keystore AES-GCM（ks-gcm 策略）

- **结论**：BDUSS 只在本机加密存储，任何页面不显示完整值（UI 只给前 4 + 后 4），日志只打长度。
- **理由**：Keystore 密钥不可导出，密文离开这台设备就解不开——这同时满足了"换设备不保留信息"
  的验收项。实测在卓易通（HarmonyOS NEXT 容器）里 `ks-gcm` 策略胜出并往返成功。
- **代价**：用户换机 / 卸载 = 登录数据永久丢失，必须重新登录。这是有意接受的。
- **出处**：`PRD_ACCEPTANCE_0.2.0.md` 第 10/13 条

### D-06 不做静默安装，一律唤醒系统安装界面

- **结论**：下载完校验 sha256 → 安装前再验包名 / versionCode / 签名指纹 → 交给系统安装器。
- **理由**：静默安装要么需要 root / 设备管理员，要么依赖会被 Google 判定为滥用的无障碍技巧。
  对个人项目这是不必要的风险。
- **代价**：用户必须手点两次确认。
- **出处**：`ROADMAP.md`「功能一」

### D-07 版本比较只用 versionCode 数字，绝不比 "0.3.0"/"0.4.0" 字符串

- **结论**：`_APP_VERSION_CODE` 是唯一判据。
- **理由**：字符串比较在 "0.10.0" vs "0.9.0" 这种地方会错。
- **出处**：`ROADMAP.md` 功能一的技术前提

### D-08 安装前必须验"包名 + versionCode + 签名指纹"，sha256 不是安全边界

- **结论**：三项都要验，签名指纹才是真边界。
- **理由**：sha256 来自发布端——发布端被篡改时，它和 APK 一起被换掉，校验照样"通过"。
  签名指纹绑的是我们私钥，攻击者拿不到。
- **出处**：`ROADMAP.md` 功能一的技术前提

## C. 产品行为（用户真机确认过，不要按"更合理"的设计改回去）

### D-09 自动签到失败不自动重试

- **结论**：每个吧单次 `sign_forum`，失败就记失败（340006 之类注明原因），不重试。
- **理由**：连续重试是最明显的机器特征，会招风控。
- **出处**：`PRD_ACCEPTANCE_0.3.0.md` 第 9 条

### D-10 只存"最近一次"自动签到结果快照，不存签到历史

- **结论**：`tiebasign_autosign.json` 只有一个快照，没有历史表。
- **理由**：隐私（历史即行为画像）+ 不需要。项目也不提供跨设备恢复。
- **出处**：`PRD_ACCEPTANCE_0.3.0.md` 第 12 条

### D-11 水贴：每个账号带自己的一组目标帖，不共用列表

- **结论**：一个账号只发自己那组帖。每天每帖默认 4 次，间隔默认 5 秒（可调 5–3600 秒，**不随机**）。
- **理由**：用户明确要求按账号区分——不同账号发同样的帖是最容易被关联的特征。
- **出处**：`ROADMAP.md` 功能二「用户确认过的行为」

### D-12 水贴只做主楼回复，楼中楼选 A（留空位）

- **结论**：`reply_mode="floor"` 返回明确的「暂不支持」，并**当天对该账号停止发送**，绝不假装成功。
- **理由**：4.7.1 只有 `get_comments` / `SubPostList` 两条**读**接口；`AddPostReqIdl.proto` 的全部
  字段里没有 `pid` / `quote_id` / `is_comment`，cmd=309731 造不出楼中楼。4.8.1 也没有。
- **代价**：功能不完整，但代码里留了分支空位，将来拿到可用接口只需加一个分支。
- **出处**：`ROADMAP.md`「能力边界」

### D-13 水贴默认不补发，与自动签到的"启动补跑"刻意相反

- **结论**：迟到超过「一个间隔 + 300 秒」的那次直接跳过并重新计时；用户可自行打开「补发」，
  每轮最多补 10 条。
- **理由**：App 关几小时后重开就连发，是最明显的机器特征。
- **出处**：`ROADMAP.md`「刻意这样设计的地方」

### D-14 手动水贴失败不计入当天次数，自动计划失败计入

- **结论**：自动计划的每次尝试都算 `sent`（给自己封顶）；手动只计成功。
- **理由**：手动是用户点出来的，一次网络抖动不该白丢当天额度，没发满还能再点一次。
- **出处**：`ROADMAP.md` 功能二（2026-10-16 实测确认）

### D-15 只有"检查更新"这一路会亮红点 + 发通知；签到/水贴的失败通知严格分开

- **结论**：手动签到失败只页面展示，不通知不红点；自动签到仅失败才通知；系统通知与 App 红点
  是**两个独立开关**；没查到新版本时什么都不提示。
- **理由**：用户对"安静"的要求很具体——只有真需要他处理的事才打扰。
- **出处**：`PRD_ACCEPTANCE_0.3.0.md` 第 5/6/7 条、`ROADMAP.md` 功能一

## D. 分发与仓库

### D-16 双源更新：GitHub 优先，Gitee 备胎

- **结论**：开始下载后 8 秒内不到 800KB（<100KB/s）就断开改从 Gitee 下。手动点「下载更新」不受
  Wi-Fi 限制；「只在 Wi-Fi 自动下载」默认开。
- **理由**：国内直连 GitHub Releases 经常极慢或断流，纯 GitHub 会让自动更新形同虚设。
- **坑**：Gitee 现在**还没有任何发行版**，返回空列表。代码把"源返回空"当**不是错误**
  （否则首次运行就误报）。所以备胎目前等于没有——Gitee 必须补发行版。
- **出处**：`ROADMAP.md` 功能一、`GITHUB_PREP.md` 第 6 节

### D-17 上传只走 git 命令行，不用网页拖拽

- **结论**：`git clone` → 清空工作树 → 铺上传集 → `git add -A` → commit → push。
- **理由**：v0.3.0 那次是网页上传的，可验证的后果有两个——**`.gitignore` 被静默丢掉**
  （浏览器上传丢弃以点开头的文件，提交者是 `GitHub <noreply@github.com>` web-flow），
  以及**网页上传没有删除操作**（9 个一次性补丁脚本至今还留在仓库里）。
  更危险的是网页上传绕过 `.gitignore`：`sign/` 里躺着一把真实私钥，哪天拖整个目录上去就公开了。
- **出处**：`GITHUB_PREP.md` 第 2 节

### D-18 同一个版本号绝不重新构建发布

- **结论**：要改就升版本号。`verify_release.sh` 拒绝覆盖 `release/` 里同名但字节不同的 APK。
- **理由**：p4a 用 `appv-<versionName>` 当"要不要重新解包 Python 代码"的标记，同版本号重编
  **不会重新解包**，装上去的 App 继续跑旧的缓存代码（实测踩过一次）。
- **出处**：`GITHUB_PREP.md` 第 7 节

### D-19 许可证 Apache-2.0，且两个平台各自携带

- **结论**：`LICENSE` 必须同时存在于 GitHub 和 Gitee 两个仓库根。
- **理由**：App 是双源更新，使用者可能从任一平台获取，授权必须跟着每一个分发副本走。
  只在建仓时勾 GitHub 的 "Add a license" 会造成"Gitee 用户处于默认保留所有权利"的不一致。
- **待补（排入 0.5.5）**：`THIRD-PARTY-NOTICES.md` —— `chardet`（LGPL-2.1）与 `certifi`（MPL-2.0）
  属弱 copyleft，分发时须附许可证文本，当前 APK 内不含任何许可证文件。
- **出处**：`README.md`「许可证」、`GITHUB_PREP.md` 第 5 节

### D-20 `java_src/` 必须入库

- **结论**：`java_src/`、`third_party/p4a-dev.tar.gz`、`third_party/p4a-webview-base-overlay.tar.gz`
  都必须提交。
- **理由**：`java_src/` 看着像实验目录，其实是**构建输入**（`patch_base_java.py` 把它打进 p4a 底座）。
  它被 `.gitignore` 排除过一次，结果是别处克隆下来构建出的 APK **静默缺少原生安装能力**。
  `p4a-dev.tar.gz` 曾经只存在于兄弟项目里，没有它新机器无法重建底座。
- **出处**：`.gitignore` 第 44–54 行的注释（那里写着"不要再加回来"）

### D-21 首期只做 Android + arm64-v8a

- **结论**：不做 iOS、不做 armeabi-v7a、不做跨设备迁移。
- **理由**：PRD 明确不需要。p4a 每多一个 ABI 就多一份构建时间与包体。
- **出处**：`PRD_ACCEPTANCE_0.3.0.md` 结尾

### D-22 深色模式用 MD3 token 全页面适配

- **结论**：`#0F1117` / `#7C9BFF` 一套 token 覆盖全部页面，靠 `prefers-color-scheme` 切换。
- **状态**：已实现，用户尚未逐页确认（验收表里是"⚠️ 已实现待最终确认"）。
- **出处**：`PRD_ACCEPTANCE_0.3.0.md` 第 15 条

### D-23 逐吧补签用「有上限并发」，不是无限制并发

- **结论**：`sign_forum` 同时最多 4 个请求（`signer.SIGN_CONCURRENCY`），每条请求前随机
  停 30~150ms 打散节奏；仍然是**每个吧单次尝试、不重试**。
- **理由**：串行时几百个吧要几分钟，这是签到慢的主因；无限制并发又会让短时间请求峰值
  明显像脚本，招风控。4 是速度与风险的折中，常量集中在一处，将来可按实测调整。
- **代价**：失败/成功的完成顺序不再稳定；进度按「已检查数」显示，不按吧顺序。
- **出处**：v0.5.5 工单第 2 项

### D-24 错误码表只收录「有出处」的码，并且用普通人能看懂的话写「原因 + 怎么办」

- **结论**：`app/tieba_codes.py` 的码表只收社区实测/上游示例能对上的码（160002、
  340006、340011、110000 等，出处写在模块 docstring）。每个码除了分类，还写
  **普通人能看懂的原因**和**怎么办**；没有出处的码不编原因，界面显示
  「百度没有给出具体原因」+「稍后再试…」，错误码只放次要位置。空 errmsg 走同一套
  人话，不再出现 errmsg / tbs / 未收录 之类的术语。
- **理由**：v0.4.0 曾把空 errmsg 一律落到「风控其他」，用户看不懂；用户明确要求
  「报错后会提示报错原因，是普通人能看懂的那种」。把「不知道」写成「风控」比不分类
  更糟；说清楚「发生了什么、你可以怎么做」才有用。
- **出处**：v0.5.5 工单第 3 项 + 2026-11-03 补充要求、`scripts/tests/test_signer.py`

### D-25 msign 失败进 warnings，不影响整体签到结果

- **结论**：`sign_forums()`（网页一键签到）失败只记 `warnings`，不算 `failed`；
  后面逐吧补签成功就是成功，不弹「自动签到失败」通知、不亮红点。
- **理由**：msign 只是批量快捷方式，失败后逐吧补签才是权威结果。v0.4.0 会因
  一个空 errmsg 把「所有吧都签到成功」误判成失败。
- **代价**：msign 的失败原因不再出现在「失败详情」，而在「提醒」区；通知只发真失败。
- **出处**：`app/autosign.py::_finalize`、v0.5.5 工单第 3 项

### D-26 日志/报告统一脱敏，并把 git 历史纳入泄露门禁

- **结论**：`sign.log`、`autosign.log`、`waterpost.log` 全部过 `app/redact.py`；
  `sign.log` 与最近一次报告落在 `ANDROID_PRIVATE`，只含账号名/掩码/错误码/原因。
  `leak_scan.sh` 在 git 仓库里自动调用 `scripts/check_history_secrets.sh` 扫历史。
- **理由**：工作树干净不等于历史干净；一次提交过的凭据删掉也还在 GitHub 上。
  而错误详情是最容易把凭据带进日志的路径（异常文本、服务端原文都可能拼进密码）。
- **出处**：v0.5.5 工单第 4 项、`docs/SECURITY_AUDIT_0.5.5.md`

### D-27 文档里的真实账号标识一律换成虚构值

- **结论**：`ROADMAP.md` 里的真实账号昵称、BDUSS 掩码、账号文件 md5 前缀已替换为
  `示例账号` / `abCD****wxyz` / `00000000…`。构建必需的 B 类本机路径（p4a 的
  `source_dir`/`local_recipes`）保持原样，因为它不是凭据，改了会直接构建失败。
- **理由**：掩码本身不是完整 BDUSS，但它与账号昵称、文件哈希一起会缩小猜测空间，
  也没有任何文档价值。
- **出处**：`docs/SECURITY_AUDIT_0.5.5.md` 第 4 节

### D-28 随机点赞：每个关注的吧各抽 1 个帖子，独立模块

- **结论**：`app/liker.py` 是签到页上的**独立模块**（与一键签到/一键水贴并列），
  不塞进吧签到流程。点一次按钮后，对该账号**每个关注的吧**各随机抽 1 个非置顶/
  非屏蔽帖，调用 `Client.agree(tid)` 点主楼赞；每个吧每天最多成功一次，失败可重试。
- **理由**：用户 2026-11-03 明确修正为“每个关注的吧随机抽一个帖子”，并要求
  独立模块、独立按钮。逐吧点赞本来就是用户要的，但仍限制每吧每天一次，避免同一吧
  被连续刷。
- **代价**：关注吧多时请求量较大（每吧 1 次 `get_threads` + 1 次 `agree`），
  所以吧之间最多 2 并发，并在页面上显示逐吧进度；失败只记详情，不影响签到。
- **出处**：v0.5.5 工单追加需求 + 2026-11-03 修正

### D-29 吧群签到按「在群里发一条自定义消息」实现，每群每天成功一次

- **结论**：`app/groupsign.py` 是签到页上的**独立模块**（独立按钮，不在吧签到
  流程里）。用 aiotieba 的 `join_chatroom` + `send_chatroom_msg(chatroom_id, fid,
  text)` 在用户配置的群里发一句话（如 «@群助手/领取今日福利»）。群通过分享链接
  添加（取 `chatroom_id`，再调公开的 `/mo/q/chat/getCardInfo` 补群名/fid）；每个
  账号只发自己配置的群；**每个群每天发送成功一次后当天不再发**，失败可重试但每天
  最多 3 次；发送失败只记 warning。
- **理由**：用户确认真正的机制就是“在指定群发消息”，不是某个群签到按钮；这是
  aiotieba 4.7.1 已经具备的能力，不需要新增未公开接口。把“发送成功”定义为
  `send_chatroom_msg` 返回无错误（以接口为准，机器人是否回复不在判定范围）。
- **读取群信息的兜底**：`getCardInfo` 走 `certifi` 的 SSL 上下文；若 Android 上
  仍失败，设置页允许手动填写「吧ID + 群名」直接添加（`fid` 是发送必需的）。
- **代价**：群消息比吧签到更显眼，所以要用户明确配置群和文案、每群每天一次；
  机器人是否真的识别这句话，需要真机验证；若某个群要求特殊 @ 或 robotc，可能
  需要后续再补参数。
- **出处**：2026-11-03 工单讨论、`app/groupsign.py`、`scripts/tests/test_groupsign.py`

### D-30 吧群签到内置常开；吧群签到/随机点赞各自有每日自动开关和时间

- **结论**：`groupsign` 去掉全局 enabled 开关，默认启用、内置在 App 里不可关闭；
  不想用时删掉账号下的群即可。`autosign` 新增 `auto_groupsign` / `auto_like`
  （默认 True）和 `groupsign_time` / `like_time`（空=跟随 global_time），
  由同一个调度线程每天启动一次；模块自己的每日记录继续防重复。
- **理由**：用户要求“默认启用、不可选择关闭”，同时“跟自动签到一样可每日自动、
  可选择开关、默认跟随全局时间也能独立设置”。把“功能开关”和“自动执行开关”
  分开：功能常开，自动执行可关。
- **代价**：默认两个自动模块开启，前台服务需要常驻；自动模块跑全部账号，
  但每个模块自己的每日成功记录/每吧记录会跳过已完成项。
- **出处**：2026-11-04 工单 v0.5.5、`app/autosign.py`、`scripts/tests/test_signer.py`

### D-31 升级到新版本后清掉旧的「已下载，待安装」

- **结论**：`updater._load()` 调 `_prune_stale`：只要 `downloaded.version_code`
  小于等于当前版本（或文件已不存在），就删除旧下载文件、清空 downloaded/latest/
  红点；设置页不再显示旧版本待安装。
- **理由**：用户通过内置更新装到新版本后，App 重启仍读到上一版留下的 JSON，
  设置页一直显示「v0.5.3 已下载，待安装」。状态必须跟当前进程版本对齐。
- **出处**：2026-11-04 工单 v0.5.5、`scripts/tests/test_updater.py`
