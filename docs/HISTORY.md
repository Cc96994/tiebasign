## 踩过的坑

### 坑 1：p4a 用缓存的 dist，只改底座会静默编出旧代码

- **现象**：改了 `java_src/`，构建成功，装到手机上发现新加的 Java 方法一个都没进 dex。
- **原因**：p4a 只在**新建 dist** 时把底座拷贝一次，之后复用 dist 就不再刷新。
- **处置**：`scripts/patch_base_java.py` 除了把 `java_src/` 打进底座，还**同时刷新 dist 里已缓存的副本**。
  两个构建脚本都会先跑它。
- **教训**：构建"成功"不等于改动"进去了"。

### 坑 2：同一个版本号重新构建，装上去仍跑旧代码

- **现象**：改了 Python 代码，版本号没动，重新构建安装，行为没变。
- **原因**：`appv-<versionName>` 是"要不要重新解包 Python 代码"的标记（底座里的
  `TiebaSignAppVersionUnpack` 补丁）。版本号不变就不会重新解包。
- **处置**：`verify_release.sh` 拒绝覆盖 `release/` 里同名但字节不同的 APK；规矩是**改了就升版本号**。
- **教训**：版本号在这里不只是显示，是构建缓存键。

### 坑 3：网页上传丢掉了 `.gitignore`

- **现象**：v0.3.0 的仓库里没有 `.gitignore`，提交者是 `GitHub <noreply@github.com>`（web-flow）。
- **原因**：浏览器上传会丢弃以点开头的文件。而 `.gitignore` 恰好是**唯一挡住 `sign/` 私钥**的东西。
- **处置**：改用 git 命令行推送（`GITHUB_PREP.md` 路线 A）。网页路线必须手工补建 `.gitignore`。
- **教训**：安全边界可能就藏在一个"不起眼的点文件"里；而工具会静默丢东西。

### 坑 4：网页上传没有删除操作，9 个废弃脚本至今留在仓库里

- **现象**：`scripts/` 下 9 个一次性补丁脚本（`patch_webview_*`、`fix_webview_*`、`verify_030.sh` 等）
  在本地早已删除（归档在 `_legacy/scripts/`），仓库里还在，且没有任何代码引用它们。
- **处置**：下次推送时一并删除；已核查删除安全。

### 坑 5：`java_src/` 被 `.gitignore` 误排除，构建出的 APK 静默缺原生能力

- **现象**：别处克隆下来构建，APK 能装能跑，但原生登录 / 保活 / 安装入口全没有。
- **原因**：`java_src/` 名字像实验目录，被加进了忽略列表。但它其实是**构建输入**。
- **处置**：从 `.gitignore` 移除，并在那里写了注释"它现在必须入库，不要再加回来"。

### 坑 6：只活在暂存目录里的文件会跟着过期消失

- **现象**：`SIGNING.md` 一度只存在于 `github_src/`（上传暂存目录）里，0.4.0 阶段暂存目录重建后，
  它在项目根消失了。
- **原因**：把"上传集"当成"文档的家"。
- **教训**：文档的权威副本必须在**项目根**，暂存目录只是它的一个副本。凡是只活在暂存目录里的，
  都会在某次重建时无声消失。

### 坑 7：`github_src/` 与 `repo_upload_*/` 会静默分叉

- **现象**：`gen_github_src.sh` 写的是 `github_src/`，真正上传用的是 `repo_upload_0.4.0/`，
  两者靠手工 `cp -a` 同步；0.4.0 这次就是手工镜像的。
- **处置**：上传前必须 `diff -r github_src repo_upload_0.4.0` 确认为空。

### 坑 8：明文 BDUSS 遗留在历史目录里

- **现象**：`_legacy/tieba_sign_app_proto/BDUSS.txt` 是**还活着的登录凭据的明文副本**，
  掩码与 App 当前账号一致。
- **处置**：2026-10-16 已移出到 `G:\学习\aiotieba\_quarantine\`（那里有 README 说明处置建议）。
- **教训**：`leak_scan.sh` 除了扫值的正则，还要用**文件名规则**抓"裸值的凭据文件"——
  `BDUSS.txt` 里可能只有一个 base64 串，值正则抓不到。扫描到 0 个文件时必须报错而不是报干净。

### 坑 9：卓易通（HarmonyOS NEXT 容器）不是标准 Android

- **现象**：在华为 Mate 60 Pro+ 的卓易通容器里，libpython 加载失败、stdlib 解包异常。
- **处置**（四条，已内置，勿删）：
  - `-Wl,-z,global` 链接选项
  - stdlib.zip 用目录形态而非 zip
  - 扫描真实 libpython 而不是硬编码名字
  - zlib 随包分发
- **教训**：用户的真机是唯一验收环境，模拟器过了不算过。

### 坑 10：`_legacy/` 让仓库看起来比实际大 30 倍

- 本地 1.1 GB，真正该进仓库的只有约 9.5 MB。`bin_m22/`（694 MB，30+ 个 debug APK）、
  `_legacy/`（338 MB）、`release*/`（60 MB）全部不该进 git。
- `.gitignore` 已覆盖，但**网页上传绕过 `.gitignore`**，所以路径依赖仍然是"用 git 推"。

### 坑 11：把「分类失败」伪装成「风控其他」

- **现象**：v0.4.0 真机上报 msign 失败只显示 `风控其他 - 错误码340011`，冒号后是空白，
  因为百度返回的 `errmsg` 是空串；而且这个错误只活在内存里，下次签到/重启就消失。
- **原因**：`_classify_server_error` 只做中文关键词匹配，空串四个分支都不匹配，于是落到
  兜底的「风控其他」——这个名字让用户以为百度说了风控，其实是「我们分类不出来」。
- **处置（0.5.2）**：错误码表用普通人能看懂的话写「原因」和「怎么办」（空 errmsg 也
  说人话，不再出现 errmsg/未收录）；msign 失败改记 `warnings` 不再误判整体失败；
  `sign.log` / 最近报告落盘，`/sign/report` 可复制导出。
- **教训**：兜底分类名要说实话，并且要告诉用户「现在能做什么」。把「不知道」写成
  「风控」会误导用户和后来的人。

### 坑 12：文档里留着真实账号掩码与昵称

- **现象**：`ROADMAP.md` 的「已验证」段落写着真实账号昵称、BDUSS 掩码和账号文件 md5 前缀。
  掩码不是完整凭据，但它没有文档价值，还会和昵称一起缩小猜测空间。
- **处置（0.5.2）**：替换为虚构值；`docs/SECURITY_AUDIT_0.5.2.md` 记录审计方法与结论。
- **教训**：保密检查不能只扫源码里的值正则，文档里的「示例」也要按真实数据对待。
